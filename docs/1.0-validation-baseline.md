# 1.0 Validation Baseline

This baseline records repository-owned validation performed against Loro `0.9.0` commit
`671d238b88a19cbc7d4d50c9d3c49740d479d8be` on August 11, 2026. It informs the 1.0 plan; it does
not replace adopting-organization evidence or approve a GA release.

## Repository Hardening Findings

1. The default `loro configure` output has workspace and wildcard-executable warnings, so the
   documented `loro config check --strict` verification fails immediately after the quick-start
   wizard. The wizard needs a strict-ready local profile or the verification contract must clearly
   distinguish local quick start from managed deployment.
2. `loro configure` writes the provider configuration before delivering its audit event. When the
   audit path is unwritable, the command fails closed with a traceback after leaving the new file
   in place. Configuration write and audit disposition need an explicit transactional or
   partial-success contract and a concise CLI error.
3. Productivity provenance sidecars identify generator, prompt preview, and artifact paths but do
   not bind generated files to cryptographic digests. Artifact integrity should be explicit before
   provenance is treated as enterprise evidence.
4. The GitHub repository has no branch or tag rulesets. Secret scanning, non-provider scanning,
   validity checks, push protection, and Dependabot security updates are disabled. These are
   release-administration blockers even though repository CI scans currently pass.
5. `v0.9.0` is an annotated tag with attested artifacts, but the tag itself is not cryptographically
   signed. The 1.0 signing and verification policy must choose and enforce a supported trust path.
6. Polaris/Iceberg, MCP, Agentic Graphs, Bedrock, and remote gateways remain experimental in the
   support matrix. The 1.0 plan must either graduate a deliberately small subset with controlled
   evidence or keep them explicitly outside the stable compatibility promise.

## Environment And External Gaps

- The local PostgreSQL recovery test could not use the host PostgreSQL 14 client against the
  PostgreSQL 16 container. This is an environment mismatch, not a product failure; the protected
  workflow passed the identical recovery drill with a compatible client.
- A secure Secret Service keyring was unavailable in the isolated test home. Credential behavior
  remains hermetically covered, but a supported production keyring needs controlled deployment
  evidence.
- A live graph execution over repository release context was intentionally rejected because the
  content and broad workspace had not been approved for provider egress. Hermetic graph execution,
  failure records, policy behavior, and protected conformance passed; a live-provider graph must
  use an approved synthetic disclosure boundary.
- Corporate identity assertions, authenticated managed-policy distribution, production
  Bubblewrap/DLP, least-privilege data roles, immutable audit anchoring, provider residency and
  period budgets, governed chat applications, production outage/load exercises, penetration
  testing, pilot results, named owners, and formal GA approval remain external requirements.

## Planning Consequence

The repository is suitable for a 1.0 stabilization branch after the six hardening findings are
resolved or explicitly scoped. Enterprise GA remains blocked until the external evidence register
has named owners, controlled references, dispositions, and approval dates. The 1.0 implementation
plan should avoid feature expansion and sequence repository hardening, release administration,
controlled deployment qualification, independent assurance, pilot closure, and final promotion.

## 0.10 Disposition

The 0.10 implementation resolves findings 1-3 in code and tests, establishes the signed-tag trust
path for finding 5, and resolves finding 6 by freezing the deliberately small stable core while
keeping the named integrations experimental. Finding 4 is partly repository code and partly
GitHub administration: release evidence now enforces signatures and provenance, while repository
rulesets, secret scanning, push protection, and Dependabot settings must be verified after the
release is pushed. The environment and external gaps remain open by design.
