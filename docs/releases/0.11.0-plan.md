# Loro 0.11.0 Release Plan

**Status:** Repository implementation, tests, documentation, and provisional release evidence are
complete. The unavailable canonical upstream source prevents formal OAP certification; this is an
explicit release limitation rather than an implied conformance claim.

## Outcome

Release `0.11.0` with experimental Open Agent Profile (OAP) v1 Level 2 support. Users can discover,
inspect, explain, and run named profiles whose requested authority is intersected with Loro policy.
Sessions can read bounded untrusted profile state and propose revision-safe `/state` updates without
allowing a profile or prior session to grant itself tools, permissions, approvals, or broader data
access.

This release does not expand Loro's stable compatibility promise. OAP remains experimental until
controlled deployments provide sufficient interoperability, security, migration, and operational
evidence. The detailed design is in the [OAP Implementation Guide](../oap-implementation-plan.md).

## Planning Corrections

The implementation guide is directionally sound, with these Loro-specific corrections:

- `SkillRegistry` is a structural reference, but it currently rejects every duplicate name. OAP
  discovery needs its own tested within-root conflict and cross-root precedence behavior.
- Permission decisions and workspace roots live in `PermissionsConfig`; executable and filesystem
  ceilings also live in `SandboxConfig`; provider hosts live in `ModelConfig`; MCP hosts live in
  `MCPConfig`. Effective-profile construction must narrow each owning configuration rather than
  pretending all limits belong to one permission object.
- `atomic_write_bytes` fsyncs the temporary file and atomically replaces the target, but does not
  fsync the parent directory. OAP durable writeback must add directory fsync where supported and
  hold `file_lock` across the complete read-check-apply-write transaction.
- The 0.10 release contract remains immutable. Because 0.11 adds CLI, configuration, schemas, audit
  events, and support classifications, the 0.11 candidate contract must be regenerated, reviewed,
  frozen, and shipped with the new artifacts.
- The referenced upstream `open-agent-profile` repository was not discoverable from the public
  repository name during planning or implementation. Loro therefore implements the supplied guide
  provisionally, records `source_revision: null`, and does not claim formal upstream certification.
  A later release must pin and reconcile the canonical URL, immutable revision, schema/license
  provenance, fixtures, reference digests, and conformance suite when they become available.

## Batch 0: Specification And Threat Baseline

**Deliverable:** an immutable, reviewable OAP input boundary before product code is written.

- Record the canonical upstream repository, OAP v1 revision/tag, license, schema hashes, fixture
  hashes, reference implementation revision, and supported conformance requirements.
- Vendor the v1 schemas and applicable fixtures with provenance metadata; do not add a floating
  runtime dependency on the specification repository.
- Map every normative OAP requirement to implementation code, tests, documentation, or a declared
  unsupported Level 3 feature.
- Add an OAP-specific threat-model section covering hostile profiles, root spoofing, symlink/path
  escape, policy widening, state prompt injection, secret persistence, proposal escalation,
  concurrent writeback, rollback, and denial of service.
- Decide additive configuration/session compatibility. Keep config schema `1.0` only if old
  configurations remain valid and omitted profile fields have safe defaults.

**Gate:** schema and invalid fixtures run locally; provenance and license review pass; no normative
requirement is unmapped or ambiguously deferred.

## Batch 1: Documents, Digests, Discovery, And Trust

**Deliverable:** side-effect-free parsing and deterministic profile resolution.

- Add `loro.agent_profiles` document models, errors, safe YAML/JSON/Markdown loaders, canonical
  JSON, profile/spec digests, and JSON Pointer validation errors.
- Disable YAML timestamp coercion and reject duplicate role instructions between Markdown body and
  frontmatter.
- Add bounded managed, user, portable `.agents`, and preferred `.loro/agents` roots to configuration.
- Assign trust exclusively from the discovery root; discard self-declared trust.
- Reject duplicate names within a root, apply explicit cross-root precedence, report every shadowed
  profile, and reject symlink/root escapes.
- Keep discovery metadata-only and resolution free of network, installs, writes, and substitutions
  inside state.

**Gate:** all valid/invalid upstream fixtures behave as expected, digests match the reference
implementation byte-for-byte, timestamps remain strings, and root/collision/symlink tests pass.

## Batch 2: Effective Profile And Fail-Closed Narrowing

**Deliverable:** the security-critical `ResolvedProfile -> EffectiveProfile` boundary.

- Introduce immutable resolved/effective types and structured adjustments. Runtime code accepts
  only an `EffectiveProfile`.
- Intersect scalar permission decisions and evaluate policy/profile rules independently before
  taking the least-permissive result.
- Narrow workspace roots, sandbox read/write roots and executable allowlists, provider/MCP hosts,
  model routes, runtime limits, memory scopes, writeback mode, identity, and tenant constraints in
  their owning configuration domains.
- Compute tools as `policy_granted & profile_requested`, then subtract denies. Never union grants.
- Resolve exact model, fallback, tier, then configured default, recording every fallback or
  substitution.
- Resolve and contain all profile paths and symlinks before runtime construction.
- Add generative/property tests asserting that no effective dimension can outrank its policy
  ceiling, plus named regression tests for every non-negotiable narrowing rule.

**Gate:** focused security review passes; every drop/narrowing/substitution is explainable and
auditable; mutation testing or equivalent negative tests demonstrate the core intersections fail
when accidentally changed from intersection to union.

## Batch 3: Level 1 Runtime And Read-Only State

**Deliverable:** useful named agents without self-modification, serving as the Level 1 checkpoint.

- Add `--agent` to `run` and text-mode `plan`, preserving byte-identical no-profile prompt output.
- Assemble profile role content in OAP's normative order between Loro's authoritative preamble and
  postamble.
- Filter runtime tools, permissions, model selection, and budgets from the effective profile.
- Record profile name, revision, spec digest, source, and trust in backward-compatible session
  records and task-start audit context.
- Load bounded `always` context files and advertise contained `on_demand` files.
- Inject state as a delimited untrusted block. Drop whole unpinned entries under budget pressure,
  retain pinned entries, report elision, prohibit state substitution, and apply the new
  `agent_profile` data-protection surface.

**Gate:** named profiles run through mock and at least one approved live provider route; denied
tools remain unavailable; malicious state grants nothing; resume preserves profile identity; all
existing no-profile runtime tests remain unchanged.

## Batch 4: Level 2 Delta, Proposals, And Durable Writeback

**Deliverable:** revision-safe learning that can modify state and nothing else.

- Generate evidence-linked state operations from explicit user statements, recorded decisions,
  status changes, and cited content. Do not ask the model to rewrite the whole state.
- Data-protect every operation value before writing a delta or profile.
- Apply under a file lock in this order: validate, revision check, digest check, strict `/state`
  scope check, writeback ceiling, atomic apply, retention, revision bump, history append, durable
  atomic write.
- Add same-directory temporary writes, file fsync, atomic replace, and parent-directory fsync where
  supported. An interrupted transaction must leave the previous revision valid.
- Reject rather than rebase first-release conflicts and report both revisions.
- Route capability proposals through `ApprovalManager`, bind review to profile/spec digest and
  reviewer identity, and prohibit automatic proposal application at every writeback setting.
- Add recovery inventory for profile state, history, locks, and pending proposals.

**Gate:** scope escape, conflict, interrupted write, concurrent writer, retention, pinned entry,
secret redaction, proposal-auto-apply, replay, and audit-completeness tests all pass.

## Batch 5: CLI, Wizards, Conformance, And Release Qualification

**Deliverable:** an operable and accurately classified `0.11.0` release.

- Add `loro agents` list/show/explain/validate/create/digest/history/state/forget/proposals/review/apply
  commands and `loro setup agents`. Keep `explain` content-free and make effective adjustments the
  primary output.
- Document profile authoring, configuration, trust/precedence, security boundaries, state,
  writeback, proposals, backup/recovery, and troubleshooting.
- Add every profile audit event to the inventory and release evidence checks.
- Publish `docs/oap-conformance.json` with the exact pinned spec revision, Level 2 claims, encodings,
  discovery roots, evidence paths, and unimplemented Level 3 features.
- Add OAP as experimental in support/interoperability matrices and regenerate the reviewed 0.11
  release contract, manifest, SBOM, checksums, and readiness evidence.
- Add a protected OAP conformance workflow using pinned upstream fixtures on Python 3.11 and 3.14;
  keep the normal CI matrix on Python 3.11-3.14.
- Run clean wheel/sdist installs, upgrade from 0.10.0, rollback to 0.10.0, no-profile agent smoke,
  profile agent smoke, and state/proposal persistence checks.

**Gate:** all repository and hosted checks pass for the exact signed release commit and built
artifacts; docs and CLI command contracts agree; public artifacts independently verify.

## Deferred From 0.11.0

- `extends` composition;
- profile-selected MCP servers or Agent Skills;
- runtime subagent delegation;
- external profile memory stores;
- Agentic Graph nodes referencing profiles;
- automatic conflict rebasing;
- multi-tenant support beyond explicitly documented single-identity behavior;
- promotion of OAP into the stable 1.0 compatibility promise.

## Definition Of Done

`0.11.0` is complete only when OAP Level 2 behavior is implemented and evidenced, all ten
non-negotiables in the implementation guide have named regression tests, the no-profile path is
compatible with 0.10, every new persistent record has upgrade/rollback/recovery coverage, all
claims are represented in machine-readable matrices and conformance evidence, and the signed PyPI
and GitHub artifacts pass independent consumer verification.
