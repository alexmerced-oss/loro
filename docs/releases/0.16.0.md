# Loro 0.16.0

Loro `0.16.0` completes the local browser workspace introduced in `0.15.2`. That release put chat,
bots, profiles, and settings in the browser; the parts of Loro that make it Loro — Agentic Graphs,
the evidence trail, and memory — were still reachable only from the CLI, so a screenshot of
`loro web` could have been any chat application. This release closes that gap and makes a turn
survive the page watching it.

## Highlights

- **Agentic Graphs in the browser.** Loro implements AGS conformance level 3 and none of that
  runtime was reachable from its own interface. The Graphs view discovers, validates, plans, and
  runs graphs through the same governed executor, presents nodes as a Kanban moving through
  pending, in progress, and complete, holds human gates for an explicit decision, and supports
  blank-board authoring, adding cards, export, and AI-drafted graphs.
- **Governance.** A read-only evidence surface: resolved identity, tenant and roles, runtime
  budgets, sandbox posture, approval mode, policy explanation for a hypothetical request, and the
  audit record with hash-chain verification and filtering by event type. Nothing on the screen can
  grant authority or mutate state.
- **Memory.** Local memories, the proposal queue, and governed shared memory were terminal-only,
  so the memory shaping every reply was invisible from the interface displaying those replies.
  Accepting a proposal writes a local memory or stages a shared draft exactly as the CLI does.
- **Declining a memory proposal is newly possible at all.** Nothing anywhere could decline one: the
  CLI only accepts, so the queue could only grow and an unwanted proposal stayed pending forever.
  Both decisions are audited.
- **Reconnection.** A chat reply and a graph run each outlive the page watching them. Both stream
  an append-only log from a cursor, so a dropped connection or a page reload resumes rather than
  losing the turn.
- **First run.** Loro is configured per folder and the browser assumed that had already happened,
  so a fresh project produced a composer whose first message failed with a provider error and no
  explanation. A setup panel now reports the same readiness `loro get-started` does and selects a
  provider and model. It never accepts a credential.
- **Themes, keyboard, and rendered replies.** Light and dark themes with a system option, a
  keyboard model covering every view, and assistant markdown rendered rather than shown raw.

## Fixes

- The event stream was cursor-capable and the client ignored it, requesting the whole log every
  time and clearing the run on any error, so a dropped connection blanked the board while the run
  carried on server-side. A comment claiming otherwise was wrong.
- Run handles were never evicted. They are held so a browser can reattach after a reload, not as
  history, so a long session accumulated every run it had executed along with that run's whole
  event log.
- Assistant output is treated as untrusted in the renderer: text is escaped before any markup is
  introduced, raw HTML never becomes elements, and `javascript:` and `data:` URLs never become
  anchors.

## Accessibility

Two audit passes run against a live server, because the properties that matter are computed styles
against real backgrounds rather than anything a unit test can assert. The first covers contrast in
both themes, accessible names, heading structure, pointer-target size, clipped text, and horizontal
overflow; the second covers the tab ring, focus indication, `prefers-reduced-motion`, 200% zoom,
and narrow viewports.

Fixed: small muted text between 2.6:1 and 4.4:1 across roughly twenty labels, below the 4.5:1 AA
threshold for text that size; chips that set no background and so fell back to the user agent's
grey, which does not follow the theme, leaving light grey on light grey in dark mode; and fields
that set `outline:0` at a specificity which also defeated `:focus-visible`, so a keyboard user
could not tell which field was focused.

## Security And Operations

Loopback binding, per-launch authorization, CSRF enforcement, same-origin validation, Host and
Origin checks, content security policy, and `no-store` response policy are unchanged from `0.15.2`.

The Governance view is read-only throughout. The Memory view's only mutation is deciding a
proposal, and both outcomes are written to the audit record. Graph runs continue to hold human
gates for an explicit decision, and a reattaching browser re-renders an outstanding gate or
approval so a resumed run is never left waiting on a question nobody can see.

## Compatibility

The deliberately limited stable `0.10` core and provisional OAP Level 3 classification are
unchanged. The local Web UI remains an additive experimental extension in the support matrix.
Existing CLI behavior and configuration files remain compatible.

## Verification

- 720 Python tests pass with 3 environment-dependent skips, and 29 frontend tests pass.
- The committed frontend bundle is checked against its source in CI; a stale bundle fails the
  build.
- Both accessibility passes are clean across every view in both themes.

## Install

```bash
python -m pip install --upgrade "loro-agent[webui]==0.16.0"
loro web
```

CLI-only installations remain available through `python -m pip install loro-agent==0.16.0`.
