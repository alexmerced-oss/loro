# Loro 0.4.1

Loro 0.4.1 is a security and reliability patch for the 0.4 release line. It closes five
release-audit findings and includes the additive TrustedRouter and Prime Intellect provider
profiles developed after 0.4.0.

## Security And Correctness Fixes

- Native provider tool arguments now pass through the managed `model_output` data-protection
  policy before execution. Nested strings are redacted or blocked exactly like textual tool
  directives. Provider wire metadata needed for protocol round trips is recursively protected
  before it is retained for later turns.
- Iceberg shared-memory writes use stable draft-derived identifiers and existing lifecycle event
  identifiers for idempotency. Loro writes provenance before state, detects completed appends, and
  can safely complete a partial operation when the same draft or lifecycle operation ID is
  retried. `loro memory lifecycle --operation-id` exposes that recovery contract to operators.
- Offset-aware datetimes are converted to UTC before being stored in Iceberg `TIMESTAMP` fields,
  preventing shifted expiry and lifecycle times.
- Gateway replay-ledger persistence failures roll back in-memory deduplication state and release
  pending queue capacity. Executor submission failures also remove the replay marker, allowing the
  signed platform request to be retried.
- Package and CLI metadata now consistently identify the release as `0.4.1`.

## Provider Profiles

- TrustedRouter is available as `trustedrouter` with aliases `trusted`, `trusted-provider`, and
  `trusted-router`, using its OpenAI-compatible endpoint and routing models.
- Prime Intellect Inference is available as `prime-intellect` with aliases `prime`,
  `primeintellect`, and `pinference`. `PRIME_TEAM_ID` optionally supplies the
  `X-Prime-Team-ID` header for team billing.

## Compatibility

- Python 3.11 through 3.14 remain supported.
- Existing configuration remains valid.
- Iceberg identifiers for a given draft are now deterministic. Retrying the same persisted draft
  no longer creates another memory record.
- The documented Iceberg write contract is audit-first and retryable because Iceberg does not
  provide cross-table transactions. Operators should alert on failed writes and retry or reconcile
  the same operation promptly.

## Verification

The release candidate must pass standard CI, Security Evidence, AGS and MCP conformance,
distribution and Twine validation, clean-wheel CLI and bundled-Skill smoke tests, and tag/version
agreement in Release Evidence. Production Postgres, Polaris/Iceberg, provider, gateway, identity,
and audit-destination evidence remains deployment-specific.
