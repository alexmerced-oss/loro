# Loro 0.10.0

Loro `0.10.0` is the stabilization release before 1.0. It resolves the repository-owned findings
from the 1.0 validation baseline without promoting experimental integrations or claiming that an
adopting organization has completed its external enterprise gates.

## Highlights

- New provider configurations are strict-ready by default: the current workspace is explicit and
  shell/MCP executable allowlists contain no wildcards.
- Provider configuration writes are atomic. A required audit-delivery failure restores the exact
  previous file, or removes a newly created file, and returns a concise CLI error.
- Productivity provenance schema `1.0` binds every generated file to its byte count and SHA-256
  digest. `loro artifacts verify` detects missing or modified outputs.
- Release tags use the documented SSH signing key. Protected release evidence verifies the tag,
  built-wheel strict setup, provenance integrity, package metadata, SBOM, checksums, and Sigstore
  artifact attestations.
- The 1.0 stable-core boundary is explicit. Linux, Python 3.11-3.14, local/Postgres memory,
  OpenAI-compatible/Anthropic/Gemini protocols, Agent Skills and Claude/Pi Skill import, coding
  tools, and productivity artifacts form the supported candidate surface. Iceberg/Polaris, MCP,
  Agentic Graphs, Bedrock, and remote gateways remain experimental.

## Compatibility

Configuration remains schema `1.0`, Postgres memory remains schema `2`, and existing provider
configuration files retain their policy sections when the provider wizard is rerun. Artifact
provenance generated before 0.10 does not contain digest bindings and therefore does not pass the
new verifier; regenerate the artifact to create schema `1.0` provenance.

## Upgrade And Verification

```bash
python -m pip install --upgrade loro-agent==0.10.0
loro --version
loro config check --strict
loro providers conformance
loro operations release-readiness --strict
```

For a fresh local project, `loro configure mock` now creates a strict-ready profile. Existing
profiles are preserved and should be hardened deliberately with the setup wizards or managed
configuration.

## External Gates

Corporate identity and managed-policy trust, production sandbox and data controls, immutable
audit retention, governed provider/chat applications, production recovery evidence, penetration
testing, pilot closure, named ownership, and formal security/privacy/legal/operations approval
remain adopting-organization responsibilities documented in the external requirements register.
