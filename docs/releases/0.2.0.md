# Loro 0.2.0

Loro 0.2.0 is the first enterprise-hardening release of the Python CLI agent harness. It remains
alpha software: repository controls are implemented and tested, while production identity,
infrastructure, governance, and assurance evidence must be supplied by each adopting enterprise.

## Highlights

- Explicit shared-memory correction, deletion, expiration, legal hold, release, provenance,
  retention, approval, and audit controls for Postgres and Iceberg.
- Process-safe JSONL audit writes and a backward-compatible SHA-256 integrity chain with
  `loro audit verify` and optional external final-hash anchors.
- Required managed-policy mode and exact-byte aggregate digest verification before TOML parsing.
- Per-task model byte, input/output token, configured cost, tool-call, and step budgets, including
  pre-request input checks and content-free usage persistence.
- Bounded provider retries for network failures, timeouts, HTTP 429, and HTTP 5xx responses, with
  environment-backed enterprise CA bundle and proxy configuration.
- A hermetic managed-identity-to-approval-to-tool-to-session-to-audit end-to-end test and a real
  ephemeral Postgres lifecycle integration test.
- Weekly Postgres and pinned Apache Polaris 1.5.0 quickstart CI, plus manual credentialed Polaris
  integration support.
- Pinned dependency, Bandit, secret-drift, license, CycloneDX SBOM, overall coverage, and
  security-module coverage gates.
- Tagged release builds with SHA-256 checksums and GitHub/Sigstore build-provenance attestations.

## Compatibility

- Python 3.11 or newer.
- Configuration remains compatible with 0.1.x; all new fields have defaults.
- Existing unchained audit JSONL remains readable. The first 0.2.0 event binds the exact legacy
  prefix and starts the integrity chain.
- Postgres schema application adds lifecycle columns idempotently. Review and back up production
  databases before applying migrations.

## Release Evidence

The release commit must pass standard CI and Security Evidence. The `v0.2.0` tag produces the
wheel, source archive, checksums, and provenance attestation in protected GitHub Actions.

The detect-secrets baseline contains 45 visible, unresolved candidates, primarily configuration
key names, documented examples, and test fixtures. They have not been bulk-suppressed. An
enterprise release owner and security reviewer must adjudicate them line by line before treating
the repository as organization-approved.

Production deployment also requires the identity, sandbox, DLP, database, Polaris, audit/SIEM,
gateway, distributed-budget, operations, penetration-test, and sign-off evidence listed in
[External Enterprise Requirements](../external-enterprise-requirements.md).
